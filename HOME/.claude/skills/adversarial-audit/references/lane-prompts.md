# レーンプロンプトの雛形

実際にレーンを展開するときに読む。`<>` を埋めて使う。

雛形をそのまま貼らず、**担当セルの背景（既知の事実・既存テスト・関連文書の場所）を具体的に埋める**こと。背景が薄いと、レーンは既に分かっていることを再発見するのに時間を使う。

---

## Phase 1 — 仮説形成レーン

```
あなたは <対象> の入口監査における「Phase 1 仮説形成レーン <ID>」です。
**読むだけ**（コード変更・テスト実行・外部への書き込みは一切しない）。

## 担当セル
<入口> × 失敗クラス <A/B/C/...>

## 背景（既知の事実）
<パース・検証の実装場所を file:line で>
<既に固定されているテストの名前と、それが何を守っているか>
<関連する設計文書の場所。読ませたいなら明示する>

## 調べること
<3〜7 項目。各項目は「〜か?」の形で、答えが真偽か数値になるように書く>
<「〜を確認せよ」と書くときは、確認結果を報告に含めることまで指示する>

## 特に潰しにいってほしい点
<この仮説が成立しないとしたらどこか、を先に書いておく。>
<レーン自身に自己反証させると、誤報が減る>

## 自己検証（必須）
報告に書く file:line は**実際に開いて確認してから**書くこと。
記憶や推測で経路・行番号・件数を書かない。確認していないものは
「未確認」と明記する。誤りを含む報告は、報告が無いより有害。

## 成果物フォーマット（厳守）
各仮説を次の形で書く。**「危なそう」だけの主張は出力しない。
観測可能な指標と予測値が書けない仮説は捨てる。**

## H-<ID>-<n>: <一行の主張>
- 分類: <失敗クラス>
- 具体的な入力: <実際に構成できる形>
- 前提となる状態: <必要な事前状態。無ければ「無し」と明記>
- 経路: <file:line> → <file:line> → <到達シンク>
- 導出: <量や回数を主張するなら、定数と式を示す>
- 観測可能な指標: <何を測れば真偽が決まるか>
- 予測値: <その指標がいくつになると主張するのか>
- 数値の出所: 定数由来 / 実測 / 外挿 のいずれか（必須）
- 既存テストで固定されているか: <テスト名 or 「無い」>
- 反証されるとしたら: <自分の主張が偽になる最も可能性の高い理由>
- 自信度: 高 / 中 / 低

## 必ず別セクションで報告すること
- 「## 該当なしと判断したもの」— 調べたが仮説にならなかった項目と**その理由**。
  これは格子の空白を閉じる成果物であり、仮説と同等に価値がある。
- 「## 暗黙の不変条件」— このセルが前提としている条件の列挙。
  破れたときに何が起きるかも書く。仮説 0 件でもこれは必ず出す。

仮説 0 件は正当な結果。事実に基づかない推測で埋めない。
```

### 調べることの書き方

悪い例: 「メモリリークが無いか調べる」
良い例: 「同じ入口を N 回踏んだときに解放されない資源はあるか。dispose 相当が全経路を通るか。`<関連ファイル>` を読み、`<既知の同型事例>` と同じ形のものを探す」

悪い例: 「量の問題を調べる」
良い例: 「上限 X はどの時点で効くか。上限に達するまでに確保されるものは何バイトか。中断後に解放されるか。**到達できる最大の構成を 1 つ具体的に指名せよ**」

「最悪ケースを 1 つ指名させる」形は強い。抽象的な懸念が具体的な入力に落ちる。

---

## Phase 2 — 反証レーン

視点ごとに別のレーンを立てる。同じ仮説群を別の角度から攻める。

```
あなたは <対象> の入口監査における **Phase 2 = 反証** のレーンです。
**読むだけ**。

## あなたの役割
**仮説を潰すこと。** 既定は「反証された」。生き残らせるには、
あなたが反証の根拠を出せないことが必要です。
「危なそうだから残す」は禁止。反証できなければ「反証できなかった」と明記。

## あなたの視点: <上流+再現性 / 下流+既存テスト>
- 上流: シンクに届く前のより手前の層で既に棄却されないか
- 再現: その入力・操作列は**実際に構成できるか**。前提状態は作れるか
- 下流: シンクに届いても二重の門が実害を止めないか。
        「起きるが誰も困らない」なら実質反証
- 既存テスト: その性質を既に固定しているテストが無いか。必ず自分で検索する

## 反証の型（どれか 1 つでも成立すれば棄却）
1. 上流で落ちる  2. 下流で吸収される  3. 前提が偽  4. 既にテストが固定している

## 検証対象
<仮説を 3〜8 件。主張・入力・経路・予測値をそのまま貼る>

## 特に潰しにいってほしい点
<各仮説について、最も崩れやすい前提を名指しする>
<「この主張は X を前提にしているが、X を自分で確認せよ」の形が効く>

## 必ず区別すること
「**仕様として意図された挙動**」と「**見落とし**」を分けて報告すること。
設計文書・コードコメントがその挙動を宣言していないかを確認する。
宣言されているなら、それは発見ではない。

## 数値について
数値の主張は「定数から導けた」「実測から取った」「外挿にすぎない」の
いずれかを必ず明記する。外挿の数値は、それ自体が反証の対象になる。

## 出力形式（厳守）
## H-<id>: 反証成功 / 反証できなかった
- 判定根拠: <file:line を伴う具体的な事実>
- 反証の型: 1/2/3/4（反証成功時のみ）
- 残る部分: <一部だけ反証できた場合、何が残るか>

最後に「## 総括」として、**修正に進めるべき仮説だけ**を列挙。
事実に基づかない推測で埋めない。
```

### 反証レーンへの背景の渡し方

仮説を貼るときは**主張だけでなく、その仮説が依拠している前提を明示する**。反証者はそこを攻める。

```
**H-X-1**: <主張>。根拠は <前提 A> と <前提 B>。
```

こう書いておくと、反証者は「前提 A を自分で確認する」から始められる。実測では、この形で渡した仮説のうち複数が「前提 A が偽」で落ちた。

---

## 監査者（オーケストレータ）側の心得

- **レーンの報告をそのまま信じない。** 修正に進めるものは、自分でもコードを開いて裏を取る。実測では、レーンが「唯一の反証筋」と申告した箇所を自分で確認して確定に持ち込めた例と、レーンの前提誤りを自分で見つけた例の両方があった。
- **レーンが自分の指示の誤りを訂正してきたら、それを採用する。** 実測では「この機能は実験フラグで既定オフのはず」という指示の前提をレーンが調べて「既定 ON」と訂正してきた。指示側の誤りは珍しくない。
- **完了通知を受けたら、その都度、地図の進捗表を更新する。** 全部揃ってからまとめて書くと、途中経過が見えない。
- **編集は、そのファイルを読んでいるレーンが終わってから。** 走行中のレーンが読むコードを書き換えると、報告と実体がずれる。新規ファイルの作成は安全。
